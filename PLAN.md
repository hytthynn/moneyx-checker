# План разработки Telegram-бота для мониторинга курса Money-X

Дата анализа: 23 сентября 2026 года.

## 1. Цель

Разработать приватного Telegram-бота, который:

- каждый час, по умолчанию в `HH:02` по часовому поясу `Europe/Moscow`, получает актуальные курсы всех криптовалют, доступных на странице пополнения Money-X;
- отправляет один сводный отчёт в выбранную группу или супергруппу Telegram;
- позволяет из Telegram вручную проверить курс, указать ID группы для рассылки, сменить домен, обновить авторизацию, изменить минуту запуска, приостановить и возобновить рассылку;
- может быть развёрнут на Vercel с Telegram webhook и serverless-хранилищем;
- не создаёт заявки на пополнение и не выполняет финансовые операции;
- безопасно хранит минимально необходимый набор секретов.

## 2. Что установлено при анализе сайта

Текущий веб-домен: `https://mxc1n.com`.

Клиент Money-X построен на Nuxt. В актуальном клиентском коде API-домен формируется так:

```text
веб-домен: https://mxc1n.com
API:       https://api.mxc1n.com
```

При смене зеркала используется та же схема: `https://api.<новый-домен>`, если конфигурация сайта явно не задаёт другой API URL.

Найдены запросы страницы пополнения:

| Назначение | Метод и путь | Примечание |
|---|---|---|
| Проверка сессии | `GET /v3/api/me` | Успешная авторизация должна вернуть непустого пользователя |
| Начальные данные пополнения | `GET /v3/api/deposit/index` | Содержит доступные способы пополнения |
| Список криптовалют и сетей | `POST /v3/api/deposit/crypto/list` | Тело запроса пустое |
| Данные выбранной криптовалюты | `POST /v3/api/deposit/crypto/wallet` | JSON: `network` и `currency` |

Без авторизации `POST https://api.mxc1n.com/v3/api/deposit/crypto/list` отвечает `401 Unauthenticated`.

После выбора валюты интерфейс берёт поле `rate` из ответа `crypto/wallet`. Видимый курс формируется для конкретной пары `currency + network`. Например, `USDT (TRC-20)` нужно считать отдельной строкой от USDT в другой сети.

В текущем клиенте значение для интерфейса проходит внутреннее преобразование `rate * 10`, после чего форматируется в рублях с точностью до трёх знаков. Перед реализацией это необходимо подтвердить на одном реальном авторизованном ответе, сопоставив результат с числом на странице. Бот должен повторять видимый курс Money-X, а не показывать необработанное значение API.

### Важное ограничение

`crypto/wallet` возвращает в том числе персональный адрес пополнения. По коду фронтенда этот запрос выглядит как получение/выдача адреса, а не создание заявки, но это всё равно POST-запрос. До циклического опроса всех валют нужно подтвердить, что запрос:

- не создаёт заявку на пополнение;
- не генерирует новый адрес при каждом вызове;
- не имеет жёсткого лимита частоты;
- действительно является единственным источником курса либо список `crypto/list` не содержит курс сразу.

Если курс уже присутствует в `crypto/list`, бот должен использовать список и не вызывать `crypto/wallet` для каждой строки.

## 3. Какие cookie нужны

Значения со скриншота намеренно не перенесены в этот файл.

| Cookie | Роль | Решение для бота |
|---|---|---|
| `token` | Основной токен входа. Фронтенд превращает его в заголовок `Authorization: Bearer <token>` | Обязателен |
| `mxi_token` | Выдаётся одновременно с `token`, но не используется фронтендом как основной признак входа | Поддержать как необязательный для совместимости |
| `last_fp` | Состояние fingerprint/антифрод-механизма | Не добавлять по умолчанию; только если API явно потребует |
| `_cf_bm` | Краткоживущий Cloudflare Bot Management cookie | Не является cookie аккаунта; не хранить постоянно |
| `animation`, `bonusMode`, `sound` | Настройки интерфейса | Не нужны |
| `intercom-device-id-*`, `intercom-id-*`, `intercom-session-*` | Чат поддержки Intercom | Не нужны |
| `_ym_*`, `yandexuid`, `yuidss`, `bh`, `i`, `L`, `Session_id`, `sessionid2`, `yandex_login`, `sessar`, `yp`, `yashr` и подобные | Яндекс/Метрика/браузерная аналитика | Не нужны |

Порядок проверки авторизации:

1. Отправить `GET /v3/api/me` только с `Authorization: Bearer <token>`.
2. Убедиться, что `data.user` не равен `null`.
3. Проверить `crypto/list` и один `crypto/wallet`.
4. Только если сервер отклоняет запрос, повторить с cookie `mxi_token`.
5. Не импортировать весь браузерный Cookie header и не сохранять аналитические cookie.

Скриншот содержит значение активного `token`. Перед использованием бота рекомендуется выйти из Money-X и войти снова, чтобы прежний токен был заменён. Новый токен нельзя коммитить, писать в логи или отправлять в общий чат.

## 4. Предлагаемый стек

- Python 3.12+;
- `aiogram` для Telegram Bot API;
- `httpx` для асинхронных HTTP-запросов;
- Telegram webhook вместо long polling при деплое на Vercel;
- внешний cronjob для вызова защищённой Vercel Function;
- Supabase PostgreSQL для настроек, истории, блокировок и состояния рассылки;
- Supabase используется и локально, и на Vercel; локальная SQLite не поддерживается;
- `cryptography` для шифрования токена в базе;
- `pydantic-settings` для несекретной конфигурации и ключей окружения;
- `pytest` и HTTP-моки для тестов.

Все прямые зависимости зафиксированы в единственном `requirements.txt`.

## 5. Архитектура

```text
Telegram ---- webhook ---- Vercel Function
                              |
                              +---- Settings repository (PostgreSQL)
                              |       +-- домен и история запусков
                              |       +-- зашифрованные token/mxi_token
                              |
Внешний cronjob --------------+---- MoneyX client ---- Auth validator
                                      |
                                      +-- список currency + network
                                      +-- нормализация курса
                                      |
                                      v
                                  Telegram sender
```

Модули:

- `bot/handlers.py` — команды и проверка администратора;
- `moneyx/client.py` — API-клиент, заголовки, таймауты, повторные попытки;
- `moneyx/models.py` — строгие модели ответов API;
- `moneyx/rates.py` — получение списка, дедупликация и преобразование курса;
- `services/jobs.py` — идемпотентный почасовой запуск и блокировка от наложений;
- `services/notifier.py` — форматирование и разбиение длинных сообщений;
- `storage/repository.py` — PostgreSQL, миграции и шифрование секретов;
- `api/telegram_webhook.py` — HTTPS endpoint для обновлений Telegram;
- `api/hourly_cron.py` — защищённый endpoint почасовой рассылки;
- `config.py` — переменные окружения;
- `main.py` — локальный запуск и общая сборка приложения;
- `vercel.json` — настройки serverless-функции без встроенного cron.

## 6. Команды бота

Доступ разрешён только `ADMIN_TELEGRAM_ID` и только в личном чате с ботом. Сообщения и команды в группе игнорируются.

| Команда | Назначение |
|---|---|
| `/start`, `/help` | Краткая справка |
| `/status` | Домен, API-домен, группа назначения, расписание, авторизация, последняя проверка |
| `/check` | Немедленно получить курсы и отправить их в настроенную группу |
| `/domain` | Показать текущий домен |
| `/domain_set <host>` | Проверить и сохранить новое зеркало |
| `/auth_set` | Запустить приватный пошаговый ввод `token` и, при необходимости, `mxi_token` |
| `/auth_status` | Проверить сессию без вывода токена |
| `/auth_clear` | Удалить сохранённую авторизацию после подтверждения |

При `/auth_set` бот должен:

- принимать только приватный чат администратора;
- сразу удалять сообщение пользователя с секретом;
- никогда не повторять значение токена в ответе;
- маскировать его в диагностике, например `eyJ…9e`;
- выполнить `/me`, затем тест получения списка;
- сохранять секрет только после успешной проверки.

Более безопасная альтернатива должна быть описана в README: использовать локальную административную команду `scripts.set_auth`, не передавая токен через Telegram.

### Настройка группы для рассылки

ID группы задаётся только переменной `TELEGRAM_GROUP_ID`. Бота необходимо заранее добавить в эту группу с правом отправлять сообщения.

Правила работы с группами:

- валидировать `TELEGRAM_GROUP_ID` как отрицательное знаковое 64-битное число;
- при ошибке `403 bot was kicked` или `chat not found` один раз уведомить администратора в личном чате, не отключая следующие запуски;
- не позволять участникам группы просматривать домен, токены и другие административные настройки.

## 7. Смена домена

Алгоритм `/domain_set`:

1. Принять hostname или HTTPS URL без пути.
2. Разрешать только HTTPS.
3. Запретить IP-адреса, localhost, приватные и link-local сети, пользовательские данные в URL, нестандартный порт и редирект на приватный адрес. Это защищает от SSRF.
4. Открыть главную страницу и определить конфигурацию Nuxt.
5. Получить `apiBase`; если оно пустое, построить `https://api.<hostname>` по логике текущего сайта.
6. Проверить сертификат, `GET /v3/api/me` и формат ответа.
7. С текущей авторизацией проверить `crypto/list`.
8. Сохранить веб- и API-домены атомарно только после всех проверок.
9. При ошибке оставить прежний домен активным.

Токен может быть ограничен доменом/зеркалом. После смены домена бот должен явно сообщить, если требуется заново выполнить `/auth_set`.

## 8. Получение и нормализация курсов

Один цикл проверки:

1. Проверить авторизацию через `/me` либо использовать короткий кеш успешной проверки.
2. Получить список `crypto/list`.
3. Валидировать каждую запись: обязательны `currency` и `network`.
4. Сохранить исходный порядок сайта; удалить только точные дубликаты пары `(currency, network)`.
5. Получить курс самым безопасным подтверждённым способом:
   - сначала из списка, если поле курса присутствует;
   - иначе через `crypto/wallet` для каждой пары с ограниченной последовательностью/конкурентностью.
6. Преобразовать внутреннее значение точно так же, как текущая страница.
7. Не включать в результат адрес кошелька, QR-код и другие персональные данные.
8. Если часть валют не загрузилась, отправить успешные строки и отдельный список ошибок.
9. Сохранить время, домен, валюту, сеть, нормализованный курс и статус запроса в историю.

Заголовки запросов:

- `Authorization: Bearer <token>`;
- `X-Client-Currency: RUB`;
- `Accept: application/json`;
- корректные `Origin` и `Referer` текущего веб-домена;
- стабильный идентифицируемый `User-Agent` бота.

Таймаут одного запроса: ориентировочно 10–15 секунд. Повторять только сетевые ошибки, `429` и временные `5xx`, с экспоненциальной задержкой и jitter. Не повторять `401/403` циклически.

## 9. Расписание и доставка

- Часовой пояс: `Europe/Moscow`.
- Каждые 60 минут строго в минуту `02`; пауза и изменение минуты не предусмотрены.
- Во внешнем cronjob задать ежечасовый вызов в минуту `02`.
- Часовой пояс cronjob не меняет номер минуты при ежечасовом расписании. Время в отчёте форматируется в `Europe/Moscow`.
- Запрещать параллельный запуск двух проверок.
- После перезапуска не отправлять несколько пропущенных отчётов подряд.
- При кратком сбое сделать до трёх попыток; успешный отчёт отправить один раз.
- При истёкшей авторизации отправить одно уведомление и прекратить бессмысленные повторы до обновления токена.
- Создавать новый уникальный ключ для каждого вызова cron; повторный вызов должен запускать новую рассылку.
- Использовать блокировку в PostgreSQL, потому что cronjob может повторно или параллельно вызвать функцию.
- Повторы Money-X API выполняются внутри задачи, а окончательная ошибка записывается в БД и отправляется администратору.

Пример сообщения:

```text
Money-X — курсы пополнения
23.09.2026 18:02 MSK

USDT (TRC-20) — 90.167 ₽
USDT (ERC-20) — 90.167 ₽
BTC (Bitcoin) — … ₽

Домен: mxc1n.com
Обновлено: 18:02:07
```

Если сообщение превышает лимит Telegram в 4096 символов, разбить его по целым строкам и добавить номера частей.

## 10. Деплой на Vercel

### Ограничения, влияющие на архитектуру

- Vercel Functions запускаются по HTTP и не предназначены для постоянно работающего Telegram long polling или фонового `while`-планировщика.
- Telegram должен доставлять обновления через `setWebhook` на production URL вида `https://<project-domain>/api/telegram/webhook`.
- В webhook обязательно проверить заголовок `X-Telegram-Bot-Api-Secret-Token`, заданный при `setWebhook`.
- Локальная файловая система функции не является постоянным хранилищем. Настройки, токены, история и идемпотентность должны храниться во внешнем PostgreSQL; ID группы задаётся окружением.
- Внешний cronjob вызывает функцию обычным HTTP-запросом. Endpoint должен проверять `Authorization: Bearer <CRON_SECRET>`.
- Cronjob может быть вызван параллельно, поэтому lease-блокировка в БД не позволяет проверкам накладываться; последовательные повторные вызовы разрешены.
- Функция должна укладываться в лимит времени выполнения. Для текущего объёма валют задать общий deadline ниже лимита Vercel; если полный обход не помещается, разбить работу через очередь или несколько идемпотентных заданий.

### Расписание

Встроенный Vercel Cron не используется. Внешний планировщик каждый час в `HH:02` вызывает защищённый `/api/hourly/02`.

### Постоянное хранилище

Для Vercel использовать Supabase Transaction pooler на порту `6543` с SSL, отключёнными prepared statements и `NullPool`. Минимальные таблицы:

- `settings`: веб-домен, API-домен и время последней ручной проверки;
- `secrets`: зашифрованные `token` и `mxi_token`, состояние проверки и время обновления;
- `delivery_runs`: уникальный часовой ключ, группа, статус, время начала/завершения и текст ошибки без секретов;
- `rate_snapshots`: нормализованные курсы и сети;
- `admin_alerts`: ключи уже отправленных предупреждений для защиты от повторов.

Схема создаётся только вручную: содержимое `migrations/001_initial.sql` копируется в Supabase SQL Editor. Приложение не содержит команды миграции и не изменяет схему при холодном старте функции.

### Environment Variables Vercel

- `TELEGRAM_BOT_TOKEN` — токен BotFather;
- `ADMIN_TELEGRAM_ID` — единственный администратор команд;
- `TELEGRAM_GROUP_ID` — целевая группа для отчётов;
- `TELEGRAM_WEBHOOK_SECRET` — секрет проверки webhook;
- `CRON_SECRET` — отдельный секрет cron endpoint;
- `APP_ENCRYPTION_KEY` — ключ шифрования Money-X токенов;
- `DATABASE_URL` — строка Supabase Transaction pooler с портом `6543`;
- `APP_BASE_URL` — стабильный production URL для регистрации webhook;

### Последовательность деплоя

1. Создать Vercel Project и Supabase Project.
2. Добавить переменные окружения только для Production.
3. Вставить `migrations/001_initial.sql` в Supabase SQL Editor и выполнить запрос.
4. Задеплоить функции и проверить `/api/health`.
5. Вызвать Telegram `setWebhook` с production URL, `secret_token` и минимальным `allowed_updates`.
6. Добавить бота в группу из `TELEGRAM_GROUP_ID`.
7. Запустить `/check`, проверить сообщение в группе и отсутствие персональных данных.
8. Настроить внешний cronjob на ежечасный вызов в минуту `02`.
9. Проверить логи одного часового окна и защиту от повторной доставки.

## 11. Безопасность

- `TELEGRAM_BOT_TOKEN`, `ADMIN_TELEGRAM_ID`, webhook/cron-секреты и ключ шифрования хранятся только в переменных окружения Vercel.
- Авторизационный `token` хранится в PostgreSQL только в зашифрованном виде.
- Локальные файлы базы, `.env` и выгрузки Vercel environment исключаются через `.gitignore`.
- Webhook и cron используют разные секреты и не принимают секрет в query string.
- Любая административная Telegram-команда проверяет `from.id` и принимается только в личном чате.
- Логи очищаются от `Authorization`, `Cookie`, адресов кошельков и тел ответов с персональными данными.
- Не использовать Playwright/Selenium и полный профиль браузера, пока прямой API работает.
- Не создавать депозит через `POST /v3/api/deposit`.
- Не обращаться к выводу средств и другим финансовым endpoint.
- Ограничить частоту ручной `/check`, чтобы не получить блокировку API.
- На `401` помечать авторизацию недействительной; на `403` не обходить защиту, а сообщать администратору.
- Никогда не коммитить реальные ответы API, HAR с токеном или скриншоты cookie.

## 12. Тесты

### Модульные

- разбор и валидация домена;
- построение API-домена;
- разбор списка валют с одинаковой валютой в разных сетях;
- преобразование `rate` в значение, совпадающее со страницей;
- маскирование секретов и очистка логов;
- разбиение Telegram-сообщения;
- дедупликация часовых запусков;
- валидация отрицательного `TELEGRAM_GROUP_ID` и 64-битного ID;

### Интеграционные с HTTP-моками

- успешные `/me`, `crypto/list`, `crypto/wallet`;
- истёкший `token` (`401`);
- необходимость/ненужность `mxi_token`;
- `429`, `5xx`, timeout и частичный ответ;
- изменение схемы JSON;
- смена домена с откатом при ошибке;
- проверка Telegram webhook secret;
- успешная и запрещённая отправка в группу, игнорирование команд из группы;
- двойной параллельный cron-вызов отправляет ровно один отчёт;
- cron-вызов без `CRON_SECRET` получает отказ.

### Ручная приёмка

1. Перевыпустить токен входом в Money-X.
2. Сравнить одну валюту из API со страницей до третьего знака.

## 14. Критерии готовности

- Курсы всех элементов списка совпадают с Money-X в момент проверки.
- Отчёт приходит каждый час в минуту `02` по Москве, рассылка всегда активна.
- Домен и авторизация меняются из приватного чата администратора.
- ID группы задаётся через `TELEGRAM_GROUP_ID` и отображается в `/status`.
- Рассылка приходит в настроенную группу, а команды работают только в личном чате администратора.
- Production-деплой Vercel работает через webhook без long polling и без зависимости от локального диска.
- Расписание запускается внешним cronjob, встроенный Vercel Cron отсутствует.
- Неверный новый домен не ломает сохранённую рабочую конфигурацию.
- Бот не создаёт депозитов и не выполняет финансовых действий.
- В логах, Git и Telegram-ответах нет открытых токенов и адресов кошельков.
- Истёкшая сессия приводит к понятному единственному уведомлению, а не к потоку ошибок.
